1. Platform Overview

Saat Saheli is a full-stack creative publishing and community platform that enables users to create, publish, and share digital books, articles, and image galleries. The platform features AI-powered content generation with multilingual (Hindi/English) support.

1.1 Key Features

  • Book Publishing: Create, edit, and publish digital books with drag-and-drop page editing
  • AI Cover Generation: Generate book covers using Stable Diffusion XL with 12+ artistic styles
  • Multilingual AI Prompts: Hindi-to-English translation for AI image prompts (Helsinki-NLP)
  • Document Upload: Import PDF and Word documents, auto-converted to page-based books
  • Flipbook Reader: Interactive page-flip style book reading experience
  • Galleries & Articles: Create and manage image galleries and articles
  • Community Chat: Real-time chat rooms across 6 categories
  • Social Features: Likes, comments, favorites, following/followers
  • Subscription Plans: Free, Premium, Gold, and Creator tiers via Stripe
  • Admin Dashboard: User management, content moderation, platform statistics

4.4 Password Reset Flow

User-Initiated Reset

  1. User calls POST /api/auth/forgot-password with email
  2. System generates a temporary password (logged server-side)
  3. User receives temp password and calls POST /api/auth/reset-password with old + new password

Admin-Initiated Reset (Super Admin Only)

  1. Super Admin calls PUT /api/auth/admin-reset-password/{userId}
  2. Password is force-reset without requiring old password verification

7. Super Admin Support — Elevated Operations

SUPER_ADMIN operations are irreversible in some cases. Exercise extreme caution with purge operations.

7.1 Super Admin Exclusive Capabilities

OperationEndpointMethodRisk Level
Change user role/api/admin/users/{userId}/rolePUTMedium
Force password reset/api/auth/admin-reset-password/{userId}PUTMedium
Purge single book permanently/api/admin/books/{bookId}/purgeDELETEHIGH
Purge all deleted books/api/admin/books/purgeDELETECRITICAL

7.2 Role Hierarchy

SUPER_ADMIN  (highest - can do everything)
    |
  ADMIN      (can manage users and content, cannot assign roles)
    |
   USER      (standard user - create and manage own content)

7.3 Role Assignment Rules

  • Only SUPER_ADMIN can assign or change user roles
  • Valid roles: USER, ADMIN, SUPER_ADMIN
  • ADMIN cannot promote other users to ADMIN or SUPER_ADMIN

Assigning a Role

PUT /api/admin/users/{userId}/role
Header: Authorization: Bearer {superadmin_jwt_token}
Body: { "role": "ADMIN" }

7.4 Purge Operations

Purge = Permanent Deletion. Data cannot be recovered after purge. Always verify before executing.
  • Single purge: Permanently deletes one book and all its pages
  • Bulk purge: Permanently deletes ALL books with status DELETED

Note: This issue was first observed on 2026-04-09. Neon free-tier suspends compute after idle periods, and Render free-tier instances can experience transient DNS failures during cold starts. The combination of both can cause intermittent UnknownHostException errors.

18. Platform Capacity & Concurrency Limits

18.1 Server Capacity Overview

ResourceCurrent LimitNotes
Tomcat Max Threads200 (Spring Boot default)Max concurrent HTTP requests the server can process simultaneously
Tomcat Min Spare Threads10 (default)Threads kept alive for immediate request handling
HikariCP Max Pool Size5 connectionsPrimary bottleneck — limited by Neon free tier
HikariCP Connection Timeout20 secondsMax wait time to acquire a DB connection from pool

18.2 Active Users — How Many Can Be Served?

Estimated Concurrent User Capacity: ~50–100 active users for typical browsing, reading, and content creation. This estimate assumes mixed workload (not all users hitting the database simultaneously).

Capacity Breakdown

ActivityConcurrent Users SupportedLimiting Factor
Browsing / Reading books~100+Tomcat threads (200); DB queries are fast (few ms)
Creating / Editing content~50–80DB writes hold connections slightly longer
AI Image Generation~10–20HF API latency (5–30s per request); Tomcat threads held during wait
Document Upload + Processing~5–10CPU-intensive PDF/Word parsing + DB + Cloudinary upload
Chat (polling every 5s)~50–80Each poll is a lightweight DB query

Why 5 DB Connections Is the Bottleneck

With only 5 HikariCP connections, any request requiring database access will queue once all 5 are in use. Most DB operations complete in under 10ms, so under normal load the pool recycles quickly. However, under heavy concurrent load (e.g., 20+ users simultaneously uploading documents or generating AI images), the 20-second connection timeout may trigger, returning 500 errors to users.

18.3 Document Upload Capacity

SettingValue
Max File Size10 MB per file
Max Request Size10 MB per request
Concurrent Uploads Supported~5–10 simultaneous uploads
Upload bottleneck: Each document upload holds a Tomcat thread for the full duration of processing (file parsing + page creation + Cloudinary image upload). A large PDF with many pages can take 10–30 seconds, blocking one of the 5 DB connections throughout. More than ~5 simultaneous uploads may cause pool exhaustion.

20.2 Manual Backup Procedure

# Export full database backup
pg_dump "${NEON_DB_URL}" --format=custom --file=saatsaheli_backup_$(date +%Y%m%d).dump

# Export specific table
pg_dump "${NEON_DB_URL}" --table=books --format=custom --file=books_backup.dump

# Restore from backup
pg_restore --dbname="${NEON_DB_URL}" --clean saatsaheli_backup_20260408.dump

20.3 File Storage Backups

Cloudinary manages all uploaded images and generated covers. Cloudinary provides its own redundancy. For critical data, use the Cloudinary Admin API to export asset lists periodically.

20.5 Disaster Recovery Steps

  1. Database corruption/loss: Use Neon PITR to restore to a point before the incident
  2. Accidental bulk delete: Restore from most recent pg_dump backup or use Neon branching to create a recovery branch
  3. Cloudinary data loss: Re-upload from local copies if available; contact Cloudinary support
  4. Complete server failure: Redeploy from GitHub repo; database is hosted externally on Neon

21.3 Database Performance Queries

-- Find slow queries
SELECT query, mean_exec_time, calls
FROM pg_stat_statements
ORDER BY mean_exec_time DESC LIMIT 10;

-- Check index usage
SELECT relname, seq_scan, idx_scan
FROM pg_stat_user_tables
ORDER BY seq_scan DESC;

-- Check table bloat
SELECT relname, n_dead_tup, n_live_tup,
  round(n_dead_tup::numeric / NULLIF(n_live_tup, 0) * 100, 2) AS dead_pct
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;

21.4 Render.com Performance Tips

  • Free tier instances spin down after 15 minutes of inactivity — first request after idle takes 30–60 seconds (cold start)
  • The ServerWakeUp component in the frontend displays a loading message during backend cold start
  • To avoid cold starts: upgrade to a paid Render plan, or set up an external health check ping (e.g., UptimeRobot) to keep the instance warm
